# FAQ と制限

## 適用範囲

**MIDI ファイルを読み書きしますか。**
しません。ホストが解析済みのノートイベントを扱います。その境界でのティックとテンポの変換は[相互運用](interoperability.md)を参照してください。

**楽譜を描画しますか。**
しません。記譜エンジンが必要とする情報 — 綴られた音、付点や連符を含む音価、小節内位置、調号 — は提供しますが、描画は行いません。

**音声解析や再生を行いますか。**
行いません。音声からのピッチ検出も再生もホストの担当です。検出した周波数は `nearestStep` で MIDI ピッチに変換すれば、ライブラリの他の部分が読めるようになります。

**実行時依存はありますか。**
ありません。パッケージは依存のない純粋な TypeScript で、すべての入り口が同期的です。

**ブラウザやワーカーで動きますか。**
動きます。ライブラリに Node 固有の API はなく、入出力はすべて JSON 互換のプレーンデータであるため、構造化クローンでワーカー境界を越えられます。

## 解析

**コード検出の信頼度が低いのはなぜですか。**
根拠が弱いためです。音数が少ない、雑音が多い、あるいは意図的に曖昧な素材には唯一の正解がありません。ライブラリは1つを選んで曖昧さを隠すのではなく、見つけたものを報告します。信頼度を表示し、ユーザーが訂正できるようにしてください。

**想定と違う調でラベル付けされるのはなぜですか。**
調区間は、ウィンドウ内のピッチクラス分布から推定されます。`minKeyBeats` が小さいと短い一時的転調が転調として読まれ、`expectedKeyBeats` が長いと転調が見落とされます。どちらも `keyTimelineFromNotes` と `detectModulations` のオプションです。[調関係と転調](key-relations-and-modulation.md)を参照してください。

**半音階的な属和音が `V7/V` ではなく `II7` になるのはなぜですか。**
主調に対してルートを名指しする綴りは常に正しく、そのコードが実際に「適用された」ものかどうかは読みだからです。`chordToRoman` に `{ applied: true }` を渡すと適用形になります。

**全音音階の箇所にローマ数字が出るのはなぜですか。**
ローマ数字を要求したためです。先に `supportsFunctionalHarmony` を確認してください。[スケールとモード](scales-and-modes.md)を参照してください。

**セクションのラベルは Verse や Chorus を意味しますか。**
意味しません。`sectionsFromNotes` は繰り返される単位を見つけ、A、B のように名付けます。どれが Verse かは曲についての判断であり、音符から決まるものではありません。

**解析は決定的ですか。**
実際には決定的で、同じ音符には同じ読みを返します。ただしバージョン管理はされていないため、検出の改善によってリリース間でラベルが変わることがあります。再現性の保証があるのは生成側だけです。[決定性とシード](determinism-and-seeding.md)を参照してください。

## 生成

**アップグレード後、同じシードで違う音が出たのはなぜですか。**
`algorithmVersion` を固定していれば変わらないはずです。固定せずに変わった場合は、既定のバージョンが上がっています。プロジェクトに記録したバージョンを固定してください。固定していて変わった場合は不具合であり、報告する価値があります。

**`complexity.rhythmic` を上げたら、残したかった音が動いたのはなぜですか。**
本来は動きません。抽選は位置で指定されるため、つまみを上げると音が増えるだけです。音が動いた場合は、シード、テンポ、小節数、格子を動かすオプションなど、他の何かも変わっています。

**`difficulty: 1` でも演奏できないパートが出るのはなぜですか。**
`difficulty` はタイミングの層だけに対する上限です。その音が楽器に存在するかどうかは `GenerationContext.instruments` から決まります。そこにプロファイルを指定し、結果を `playability` で確認してください。

**`voiceProgression` が妥協案ではなく例外を投げたのはなぜですか。**
制約を満たすボイシングが存在しなかったためです。`NoSolutionError` は、入力ではなく制約を変える必要があることを示します。音域を広げるか `maxSpacing` を上げてください。[エラーと検証](errors-and-validation.md)を参照してください。

**独自のスタイル語彙を渡せますか。**
渡せます。`GenerationContext.vocabulary` は全パート分の figures を1つのリストで受け取ります。組み込みの id を持つ項目は、その組み込みを置き換えます。

## 綴りと記譜

**ピッチクラス6が F# ではなく Gb と綴られるのはなぜですか。**
どちらも C から臨時記号6つ分の距離にあり、同点の場合はフラット側を採るためです。曲がもう一方の綴りで書かれている場合は、主音を明示的に渡してください。

**変ニ長調の平行調が嬰イ短調ではなく変ロ短調なのはなぜですか。**
調関係を5度空間で計算し、主音を5度圏から読み戻しているためです。これにより綴りが慣用的な形に保たれます。

**チェッカーが MIDI 番号ではなく綴られた音を要求するのはなぜですか。**
半音数では対斜も増2度も見えないためです。同じ2つのピッチに対して、`isForbiddenMelodicLeap(parseNote('Ab4'), parseNote('B4'))` は true、`isForbiddenMelodicLeap(68, 71)` は false になります。

**`B` がドイツ語の変ロではなく英語として読まれるのはなぜですか。**
出所の分からない単独の `B` は英語表記であることが圧倒的に多いためです。出所が分かっている場合は `system` を明示的に渡してください。

## 設計上の判断

**クラス API と関数 API の両方があるのはなぜですか。**
本体は関数です。クラスはいずれもその薄い外皮で、値とその文脈をひとまとめに保持します。呼び出しを連ねるときに、同じ事実を何度も書き直さずに済ませるためのものです。クラスは `.data` でプレーンな値を公開し、プレーンな値を受け取りもするので、両者は自由に組み合わせられます。どちらかが閉じた世界になることはありません。

**どちらを使うべきですか。**
その場で読みやすいほうです。返す答えは同じで、メンバーごとに突き合わせるテストがそれを保っています。

対象を共有する呼び出しが複数あるならクラスです。`Score` は音符と拍子とテンポと調をまとめて持つので、和声・フレーズ・セクションを読むのは、3つの関数を手で配線するのではなく3回のメソッド呼び出しになります。`Composer` は曲全体の調・テンポ・シードを持つので、各パートは1回の呼び出しで済み、文脈を毎回書き添える必要がありません。

問いが1つで、データが既に手元にあるなら関数です。あるいは、JSON だけをやり取りするプラグイン境界のように、クラス層に依存させたくないものを書くときも関数です。

**解析と生成が分かれているのはなぜですか。**
楽節を検査する処理が、それを書き換えないようにするためです。`playability` は奏者に渡された譜面に対して「演奏できるか」に答えるものであり、譜面を編集することはありません。

**スケールが名前ではなくビットマスクを持つのはなぜですか。**
12ピッチクラスの任意の部分集合が、組み込みスケールと同じようにどこでも使えるようにするためです。あわせて、所属や度数の判定が表引きではなく算術になります。

**生成したパートがプロジェクトに書き込まれず、ノートイベントとして返るのはなぜですか。**
プロジェクトを所有しているのはホストだからです。ジェネレータが返すのは素材で、それをどこに置くか、何かを置き換えるか、ユーザーがその後どう編集するかは、ライブラリが決めることではありません。
